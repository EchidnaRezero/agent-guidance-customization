# 테스트 주도 개발 (TDD)

## 개요

테스트를 먼저 씁니다. 실패하는 것을 봅니다. 통과할 만큼만 최소 코드를 씁니다.

**핵심 원칙:** 테스트가 실패하는 것을 직접 보지 않았다면, 그 테스트가 올바른 것을 검사하는지 모릅니다.

**규칙의 문구를 어기는 것은 규칙의 정신을 어기는 것입니다.**

## 언제 사용하는가

**항상 사용:**
- 새 기능
- 버그 수정
- 리팩터링
- 동작 변경

**예외는 사용자에게 물어봅니다:**
- 폐기할 프로토타입
- 생성된 코드
- 설정 파일

"이번 한 번만 TDD를 건너뛸까?"라는 생각이 들면 멈추세요. 그것은 합리화입니다.

## 철칙

```
NO PRODUCTION CODE WITHOUT A FAILING TEST FIRST
```

테스트보다 코드를 먼저 썼다면 삭제하고 다시 시작합니다.

**예외 없음:**
- "참고용"으로 보관하지 않습니다.
- 테스트를 쓰면서 "변형"하지 않습니다.
- 쳐다보지 않습니다.
- 삭제는 삭제입니다.

테스트에서 새로 구현합니다. 끝입니다.

## Red-Green-Refactor

1. **RED:** 실패하는 테스트를 씁니다.
2. **Verify RED:** 올바른 이유로 실패하는지 확인합니다.
3. **GREEN:** 통과할 만큼만 최소 코드를 씁니다.
4. **Verify GREEN:** 테스트가 통과하는지 확인합니다.
5. **REFACTOR:** 통과 상태를 유지하며 정리합니다.
6. 다음 동작에 대해 다시 RED부터 반복합니다.

### RED - 실패하는 테스트 작성

원하는 동작 하나를 보여주는 최소 테스트를 씁니다.

좋은 테스트는 이름이 명확하고, 실제 동작을 검사하며, 한 가지만 확인합니다. 나쁜 테스트는 이름이 모호하고, 실제 코드가 아니라 mock 동작만 검사합니다.

**요구사항:**
- 한 가지 동작
- 명확한 이름
- 실제 코드 사용. mock은 피할 수 없을 때만 사용합니다.

### Verify RED - 실패를 직접 확인

**필수입니다. 절대 건너뛰지 않습니다.**

```bash
npm test path/to/test.test.ts
```

확인할 것:
- 테스트가 실패합니다. 단순 오류가 아니어야 합니다.
- 실패 메시지가 예상과 맞습니다.
- 기능이 없어서 실패합니다. 오타 때문에 실패하면 안 됩니다.

**테스트가 통과하면:** 이미 있는 동작을 테스트한 것입니다. 테스트를 고칩니다.

**테스트가 오류를 내면:** 오류를 고치고, 올바르게 실패할 때까지 다시 실행합니다.

### GREEN - 최소 코드

테스트를 통과시키는 가장 단순한 코드를 씁니다.

기능을 추가로 넣거나, 다른 코드를 리팩터링하거나, 테스트 범위를 넘어 "개선"하지 않습니다.

### Verify GREEN - 통과를 직접 확인

**필수입니다.**

```bash
npm test path/to/test.test.ts
```

확인할 것:
- 테스트가 통과합니다.
- 다른 테스트도 여전히 통과합니다.
- 출력이 깨끗합니다. 오류나 경고가 없어야 합니다.

**테스트가 실패하면:** 테스트가 아니라 코드를 고칩니다.

**다른 테스트가 실패하면:** 지금 고칩니다.

### REFACTOR - 정리

green 이후에만 수행합니다.

- 중복 제거
- 이름 개선
- helper 추출

테스트는 계속 green이어야 합니다. 새 동작을 추가하지 않습니다.

## 좋은 테스트

| 품질 | 좋음 | 나쁨 |
| --- | --- | --- |
| **최소성** | 한 가지를 검사합니다. 이름에 "and"가 있으면 나눕니다. | `test('validates email and domain and whitespace')` |
| **명확성** | 이름이 동작을 설명합니다. | `test('test1')` |
| **의도 표시** | 원하는 API 사용법을 보여줍니다. | 코드가 무엇을 해야 하는지 흐립니다. |

## 순서가 중요한 이유

**"나중에 테스트를 써서 확인하겠다"**

코드 뒤에 쓴 테스트는 바로 통과합니다. 바로 통과하는 테스트는 아무것도 증명하지 못합니다. 잘못된 것을 테스트할 수 있고, 동작이 아니라 구현을 테스트할 수 있으며, 떠올리지 못한 edge case를 놓칩니다.

**"이미 수동으로 edge case를 다 테스트했다"**

수동 테스트는 임시적입니다. 기록이 없고, 코드가 바뀔 때 다시 실행하기 어렵고, 압박 속에서 빠뜨리기 쉽습니다. 자동 테스트는 매번 같은 방식으로 실행됩니다.

**"몇 시간 작업한 코드를 삭제하는 건 낭비다"**

이미 쓴 시간은 돌아오지 않습니다. 신뢰할 수 없는 코드를 유지하는 것이 기술 부채입니다. TDD로 다시 쓰면 신뢰도가 높아집니다.

**"TDD는 교조적이고, 실용적으로 적응해야 한다"**

TDD는 실용적입니다. 커밋 전 버그를 찾고, 회귀를 막고, 동작을 문서화하고, 리팩터링을 가능하게 합니다.

**"테스트를 나중에 써도 목적은 같다"**

아닙니다. 테스트-after는 "이 코드가 무엇을 하는가"를 묻습니다. 테스트-first는 "이 코드가 무엇을 해야 하는가"를 묻습니다.

## 흔한 합리화

| 변명 | 현실 |
| --- | --- |
| "너무 단순해서 테스트가 필요 없다" | 단순한 코드도 깨집니다. 테스트는 금방 씁니다. |
| "나중에 테스트하겠다" | 바로 통과하는 테스트는 증명하지 못합니다. |
| "수동으로 이미 테스트했다" | 임시 확인은 체계가 아닙니다. 기록도 재실행도 없습니다. |
| "삭제하기 아깝다" | 검증되지 않은 코드를 유지하는 것이 부채입니다. |
| "참고용으로 남기고 테스트부터 쓰겠다" | 결국 변형하게 됩니다. 삭제는 삭제입니다. |
| "탐색이 필요하다" | 괜찮습니다. 탐색 코드는 버리고 TDD로 시작합니다. |
| "테스트가 어렵다" | 설계가 불명확하다는 신호입니다. |
| "기존 코드에 테스트가 없다" | 지금 개선하면 됩니다. 기존 코드에도 테스트를 추가합니다. |

## Red Flags - 멈추고 다시 시작

- 테스트보다 코드를 먼저 작성함
- 구현 뒤에 테스트를 추가함
- 테스트가 즉시 통과함
- 왜 실패했는지 설명할 수 없음
- 테스트를 "나중에" 추가함
- "이번 한 번만" 합리화함
- "이미 수동 테스트했다"고 말함
- "테스트-after도 같은 목적"이라고 말함
- "정신이 중요하지 절차가 중요하지 않다"고 말함
- "참고용으로 보관"하거나 기존 코드를 "변형"함
- "이미 X시간 썼으니 삭제는 낭비"라고 생각함
- "TDD는 교조적이고 나는 실용적"이라고 생각함
- "이번은 다르다"고 생각함

**이 모든 경우: 코드를 삭제하고 TDD로 다시 시작합니다.**

## 버그 수정 예시 흐름

버그: 빈 이메일이 허용됨

**RED**

```typescript
test('rejects empty email', async () => {
  const result = await submitForm({ email: '' });
  expect(result.error).toBe('Email required');
});
```

**Verify RED**

```bash
$ npm test
FAIL: expected 'Email required', got undefined
```

**GREEN**

```typescript
function submitForm(data: FormData) {
  if (!data.email?.trim()) {
    return { error: 'Email required' };
  }
  // ...
}
```

**Verify GREEN**

```bash
$ npm test
PASS
```

**REFACTOR**

필요하면 여러 필드 검증을 추출합니다.

## 검증 체크리스트

완료라고 표시하기 전 확인합니다.

- [ ] 새 function/method마다 테스트가 있음
- [ ] 구현 전 각 테스트가 실패하는 것을 봄
- [ ] 각 테스트가 예상한 이유로 실패함. 오타가 아니라 기능 부재 때문임
- [ ] 각 테스트를 통과시키는 최소 코드를 작성함
- [ ] 모든 테스트가 통과함
- [ ] 출력이 깨끗함. 오류나 경고가 없음
- [ ] 테스트가 실제 코드를 사용함. mock은 피할 수 없을 때만 사용함
- [ ] edge case와 오류가 다뤄짐
- [ ] 구현이 합의한 범위와 완료 기준에 여전히 맞음
- [ ] 테스트를 통과시키는 과정에서 scope creep이 생기지 않음

모든 항목을 체크할 수 없다면 TDD를 건너뛴 것입니다. 다시 시작합니다.

## 막혔을 때

| 문제 | 해결 |
| --- | --- |
| 테스트 방법을 모르겠음 | 원하는 API를 먼저 쓰고 assertion부터 작성합니다. 사용자에게 묻습니다. |
| 테스트가 너무 복잡함 | 설계가 너무 복잡합니다. 인터페이스를 단순화합니다. |
| 모든 것을 mock해야 함 | 코드 결합도가 높습니다. dependency injection을 사용합니다. |
| 테스트 설정이 큼 | helper를 추출합니다. 그래도 복잡하면 설계를 단순화합니다. |

## 디버깅과의 연결

버그를 찾으면 그 버그를 재현하는 실패 테스트를 씁니다. TDD cycle을 따릅니다. 테스트가 수정과 회귀 방지를 증명합니다.

테스트 없이 버그를 고치지 마세요.

## 테스트 안티패턴

mock이나 test utility를 추가할 때는 흔한 함정을 피하기 위해 `@testing-anti-patterns.md`를 읽습니다.

- 실제 동작이 아니라 mock 동작을 테스트함
- production class에 test-only method를 추가함
- 의존성을 이해하지 않고 mock함

## 최종 규칙

```
Production code → test exists and failed first
Otherwise → not TDD
```

사용자 허락 없는 예외는 없습니다.
