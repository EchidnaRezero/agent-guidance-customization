# 아이디어를 설계로 구체화하기

아이디어를 바로 구현하지 말고, 대화를 통해 완성된 설계와 명세로 바꿉니다.

먼저 현재 프로젝트 상황을 이해합니다. 그다음 질문을 한 번에 하나씩 하며 아이디어를 다듬습니다. 무엇을 만들지 충분히 이해하면 설계를 제시하고, 필수 5가지를 확정한 뒤 사용자 승인을 받습니다.

<HARD-GATE>
설계를 제시하고 사용자가 승인하기 전에는 어떤 구현 스킬도 호출하지 말고, 코드를 작성하지 말고, 프로젝트를 스캐폴딩하지 말고, 구현 행동을 하지 마세요. 프로젝트가 아주 단순해 보여도 항상 적용됩니다.
</HARD-GATE>

## 안티패턴: "너무 단순해서 설계가 필요 없다"

모든 프로젝트는 이 과정을 거칩니다. 할 일 목록, 단일 함수 유틸리티, 설정 변경도 마찬가지입니다. "단순한" 프로젝트일수록 확인하지 않은 가정 때문에 시간이 낭비됩니다. 정말 단순한 작업이라면 설계는 몇 문장으로 짧아도 되지만, 반드시 제시하고 승인을 받아야 합니다.

## 체크리스트

아래 항목마다 작업을 만들고 순서대로 완료해야 합니다.

1. **프로젝트 맥락 탐색** - 파일, 문서, 최근 커밋 확인
2. **시각적 companion 제안** - 시각 질문이 포함될 주제라면 별도 메시지로 제안합니다. 명확화 질문과 합치지 않습니다.
3. **명확화 질문** - 한 번에 하나씩, 목적/제약/성공 기준을 이해합니다.
4. **2-3개 접근 방식 제안** - 장단점과 추천안을 함께 제시합니다.
5. **설계 제시 및 5가지 항목 확정** - 복잡도에 맞게 섹션을 나누고, 각 섹션 뒤 사용자 승인을 받습니다.
6. **개요 설계 문서 작성** - `docs/superpowers/specs/YYYY-MM-DD-<topic>-design.md`에 저장하고 커밋합니다.
7. **명세 자체 검토** - 자리표시자, 모순, 모호함, 범위를 빠르게 확인하고 바로 수정합니다.
8. **사용자가 작성된 명세 검토** - 진행 전 사용자에게 명세 파일 검토를 요청합니다.
9. **구현으로 전환** - 사용자가 중학생도 이해할 말로 "누구를 위한 것인지, 무엇을 하는지, 왜 도움이 되는지" 설명할 수 있을 때만 `writing-plans`를 호출합니다.

터미널 상태는 `writing-plans` 호출입니다. `frontend-design`, `mcp-builder` 또는 다른 구현 스킬을 호출하지 마세요. brainstorming 뒤에 호출할 수 있는 유일한 스킬은 `writing-plans`입니다.

## 절차

### 아이디어 이해

- 먼저 현재 프로젝트 상태를 확인합니다. 파일, 문서, 최근 커밋을 봅니다.
- 상세 질문 전에 범위를 판단합니다. 요청이 여러 독립 하위 시스템을 포함하면 즉시 분해가 필요하다고 알립니다.
- 단일 명세로 너무 크면 하위 프로젝트로 나누고, 첫 번째 하위 프로젝트만 일반 설계 흐름으로 진행합니다.
- 적절한 범위라면 질문을 한 번에 하나씩 합니다.
- 가능하면 객관식 질문을 선호하지만, 개방형 질문도 괜찮습니다.
- 목적, 제약, 성공 기준을 이해하는 데 집중합니다.
- 산출물이나 구현 경계가 불분명하면, 진행 전에 시각적 companion 또는 간단한 프로토타입 예시를 요구합니다.
- brainstorming 종료 전 반드시 5가지를 확정합니다: 목적, 의도한 사용자, 범위, 산출물과 기대 효과, 완료 기준.

### 접근 방식 탐색

- 서로 다른 2-3가지 접근 방식을 제안합니다.
- 각 접근의 트레이드오프를 설명합니다.
- 추천안을 먼저 제시하고 이유를 설명합니다.

### 설계 제시

- 무엇을 만들지 이해했다고 판단되면 설계를 제시합니다.
- 각 섹션은 복잡도에 맞춥니다. 단순하면 몇 문장, 복잡하면 200-300단어까지 가능합니다.
- 각 섹션 뒤 "여기까지 맞는지" 확인합니다.
- 아키텍처, 컴포넌트, 데이터 흐름, 오류 처리, 테스트를 포함합니다.
- brainstorming 끝에는 5가지 확정 항목을 명시합니다.
- 이해되지 않는 부분이 있으면 되돌아가서 다시 명확히 합니다.

### 고립성과 명확성을 위한 설계

- 시스템을 하나의 명확한 목적을 가진 작은 단위로 나눕니다.
- 단위들은 잘 정의된 인터페이스로 소통해야 하며, 독립적으로 이해하고 테스트할 수 있어야 합니다.
- 각 단위에 대해 "무엇을 하는가, 어떻게 쓰는가, 무엇에 의존하는가"를 답할 수 있어야 합니다.
- 내부를 읽지 않아도 단위의 역할을 이해할 수 있어야 합니다.
- 파일이 너무 커지면 너무 많은 일을 하고 있다는 신호일 수 있습니다.

### 기존 코드베이스에서 작업

- 변경 제안 전에 현재 구조를 탐색하고 기존 패턴을 따릅니다.
- 작업에 영향을 주는 기존 문제가 있으면, 현재 목표에 필요한 범위 안에서 개선을 설계에 포함합니다.
- 관련 없는 리팩터링은 제안하지 않습니다.

## 설계 이후

### 문서화

- 사람이 읽을 수 있는 개요 설계 문서를 `docs/superpowers/specs/YYYY-MM-DD-<topic>-design.md`에 작성합니다.
- 단순한 작업은 이 문서 하나면 됩니다.
- 복잡한 작업은 상세 문서를 추가할 수 있지만, 개요 문서에는 확정된 5가지 항목이 반드시 있어야 합니다.
- 이 개요 설계 문서는 `writing-plans`의 입력이 됩니다.
- 사용자 선호 위치가 있으면 그 위치가 기본값을 덮어씁니다.
- 가능하면 `elements-of-style:writing-clearly-and-concisely` 스킬을 사용합니다.
- 설계 문서를 git에 커밋합니다.

### 명세 자체 검토

개요 설계 문서를 쓴 뒤 새 눈으로 확인합니다.

1. **자리표시자 확인:** "TBD", "TODO", 미완성 섹션, 모호한 요구사항이 있으면 고칩니다.
2. **내부 일관성:** 섹션끼리 모순되는지, 아키텍처가 기능 설명과 맞는지 확인합니다.
3. **범위 확인:** 단일 구현 계획으로 충분히 좁은지, 분해가 필요한지 확인합니다.
4. **모호함 확인:** 요구사항이 두 가지로 해석될 수 있으면 하나를 선택해 명시합니다.

문제는 바로 수정합니다. 다시 별도 검토할 필요는 없습니다.

### brainstorming 완료 게이트

사용자가 중학생도 이해할 말로 프로젝트가 누구를 위한 것인지, 무엇을 하는지, 왜 도움이 되는지 설명할 수 있을 때까지 `writing-plans`로 전환하지 않습니다.

### 사용자 검토 게이트

명세 자체 검토가 끝나면 사용자에게 문서를 검토해 달라고 요청합니다.

> "Spec written and committed to `<path>`. Please review it and let me know if you want to make any changes before we start writing out the implementation plan."

사용자 응답을 기다립니다. 변경 요청이 있으면 수정하고 명세 자체 검토를 다시 수행합니다. 사용자가 승인한 뒤에만 진행합니다.

### 구현

- 상세 구현 계획을 만들기 위해 `writing-plans` 스킬을 호출합니다.
- 다른 스킬은 호출하지 않습니다. 다음 단계는 오직 `writing-plans`입니다.

## 핵심 원칙

- **한 번에 하나의 질문** - 여러 질문으로 사용자를 압박하지 않습니다.
- **객관식 선호** - 가능하면 열린 질문보다 답하기 쉽습니다.
- **YAGNI 철저 적용** - 필요 없는 기능을 설계에서 제거합니다.
- **대안 탐색** - 결정 전 항상 2-3가지 접근 방식을 제안합니다.
- **점진적 검증** - 설계를 제시하고 승인받은 뒤 이동합니다.
- **유연성** - 말이 안 되는 부분이 있으면 되돌아가서 명확히 합니다.

## Visual Companion

brainstorming 중 mockup, diagram, visual option을 보여주기 위한 브라우저 기반 companion입니다. 모드가 아니라 도구입니다. 사용자가 companion을 수락해도 모든 질문을 브라우저로 처리한다는 뜻은 아닙니다.

### companion 제안

앞으로 mockup, layout, diagram 같은 시각 자료가 도움이 될 질문이 예상되면 한 번 동의를 구합니다.

> "Some of what we're working on might be easier to explain if I can show it to you in a web browser. I can put together mockups, diagrams, comparisons, and other visuals as we go. This feature is still new and can be token-intensive. Want to try it? (Requires opening a local URL)"

이 제안은 반드시 단독 메시지여야 합니다. 명확화 질문, 맥락 요약, 다른 내용과 합치지 마세요. 위 제안만 보내고 사용자 응답을 기다립니다. 거절하면 텍스트만으로 brainstorming을 진행합니다.

### 질문별 결정

사용자가 수락한 뒤에도 각 질문마다 브라우저를 쓸지 터미널을 쓸지 판단합니다. 기준은 "사용자가 읽는 것보다 보는 것으로 더 잘 이해하는가?"입니다.

- **브라우저 사용:** mockup, wireframe, layout 비교, architecture diagram, side-by-side visual design처럼 시각적인 내용
- **터미널 사용:** requirements question, conceptual choice, tradeoff list, A/B/C/D text option, scope decision처럼 텍스트인 내용

UI 주제라고 항상 시각 질문은 아닙니다. "이 맥락에서 personality가 무슨 뜻인가?"는 개념 질문이므로 터미널을 씁니다. "어떤 wizard layout이 더 나은가?"는 시각 질문이므로 브라우저를 씁니다.

사용자가 companion에 동의하면 진행 전에 상세 가이드를 읽습니다.
