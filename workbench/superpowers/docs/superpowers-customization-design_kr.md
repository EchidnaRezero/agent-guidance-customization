# superpowers 맞춤화 차이점

이 문서는 기존 `superpowers` 설명을 다시 적지 않습니다.
여기에는 현재 `superpowers` 위에 덮어쓸 차이점만 적습니다.

## 1. 전체 방향

- 기본 흐름은 기존 `superpowers`를 그대로 따른다.
- 이 문서는 각 단계에서 무엇을 더 강하게 고정할지, 무엇을 다르게 판단할지만 정한다.
- 기존 내용과 같은 말이면 기존 `superpowers`를 다시 쓰지 않고, 여기서 정한 기준으로 덮어쓴다.

## 2. `brainstorming`에 덮어쓸 차이점

### 2.1 마지막 고정물

`brainstorming`은 아이디어를 넓게 탐색할 수 있다.
하지만 끝날 때는 반드시 아래 5가지를 고정해야 한다.

- 목적
- 예상 사용자
- 범위
- 결과물과 기대효과
- 완료 기준

### 2.2 통과 기준

아래가 안 되면 `writing-plans`로 넘어가면 안 된다.

- 사용자가 중학생의 말로 `이 프로젝트는 누가 쓰는지, 뭘 할 수 있는지, 쓰면 무엇이 좋아지는지` 설명할 수 있다
- 누가 쓸 프로젝트인지 분명하다
- 어디까지 구현하는지 분명하다
- 결과물이 어떤 형태인지 바로 떠오른다
- 넣으려는 기능이 그 사용자에게 정말 필요한지 설명할 수 있다

### 2.3 불분명할 때의 행동

결과물이나 구현 경계가 불분명하면 바로 아래 중 하나를 먼저 만든다.

- 시각화
- 간단한 프로토타입 예시

### 2.4 문서 산출물

`brainstorming` 최종 통과 결과로 사람이 읽는 기준 설계문서가 반드시 나와야 한다.

- 기능이 단순하면 설계문서 1장으로 끝낸다
- 기능이 복잡하면 세부 설계문서를 더 둘 수 있다
- 그래도 전체를 조망하는 기준 문서 1장은 반드시 둔다
- 그 기준 문서에 위 5가지가 들어가야 한다

## 3. `writing-plans`에 덮어쓸 차이점

### 3.1 시작 입력

`writing-plans`는 `brainstorming`에서 통과된 기준 설계문서를 입력으로 받아야 한다.

### 3.2 최소 산출물

`writing-plans`에서는 최소 두 종류의 문서가 나와야 한다.

1. 기술 설계 문서
2. 구현 작업표

기술 설계 문서에는 최소한 아래가 들어가야 한다.

- 프로젝트 구조
- 파일 구조
- 클래스 구조
- 주요 함수와 주요 동작

구현 작업표에는 최소한 아래가 들어가야 한다.

- 실제 구현 순서
- 작업 단위
- 어떤 순서로 만들고 확인할지

### 3.3 여기서 확정할 것

`writing-plans`에서는 아래를 확정해야 한다.

- 기술 스택
- security level
- debug logging 여부
- tests 여부와 전략
- local environment 방식
- Git 사용 계획

### 3.4 문서 검토 규칙

`writing-plans` 문서는 `brainstorming` 기준 설계문서를 벗어나지 않는지 검토해야 한다.

아래를 확인한다.

- 목적이 바뀌지 않았는지
- 예상 사용자가 바뀌지 않았는지
- 구현 범위가 몰래 늘어나지 않았는지
- 결과물 형태가 바뀌지 않았는지
- 기대효과가 다른 방향으로 바뀌지 않았는지
- 완료 기준이 빠지거나 약해지지 않았는지

### 3.5 복귀 규칙

아래가 나오면 `writing-plans`를 계속 밀지 말고 다시 `brainstorming`으로 돌아간다.

- 기술적으로 현재 목표가 너무 큼
- 구현 경계가 애매해서 작업이 자꾸 늘어남
- 보안이나 운영 부담 때문에 목표를 줄여야 함
- 결과물 형태가 기술 현실과 안 맞음

## 4. 구현 단계에 덮어쓸 차이점

### 4.1 `executing-plans`

- plan에 없는 기능을 함부로 추가하지 않는다
- 구현 중 방향이 달라지면 먼저 plan 또는 brainstorming으로 되돌아간다

### 4.2 `review/test`

- 지금 구현이 원래 범위를 넘었는지 같이 본다
- 완료 기준을 실제로 만족하는지 같이 본다
- 반복 실패가 쌓이면 원인 분석으로 넘긴다

### 4.3 `systematic-debugging`

- 반복 실패를 고치는 단계가 아니라 원인 분석 단계로 쓴다
- 원인 분석 결과 목표나 범위를 고쳐야 하면 다시 `brainstorming`으로 돌린다

## 5. 마무리 단계에 덮어쓸 차이점

### 5.1 `finishing-a-development-branch`

- commit/push가 필요할 때만 Git 관련 확인을 한다
- 첫 commit/push 전에만 repo-local `user.name`, `user.email`을 설정한다
- Git을 쓰지 않는 작업이면 이 확인은 건너뛴다

## 6. 실제 수정 순서

1. `brainstorming`에 5가지 고정물, 통과 기준, 기준 설계문서 규칙을 넣는다.
2. `writing-plans`에 2종 문서 산출물, 기술 결정 항목, 기준 문서 검토 규칙을 넣는다.
3. `executing-plans`에 plan 밖 확장 금지와 복귀 규칙을 넣는다.
4. `review/test`와 `systematic-debugging`에 범위 초과, 완료 기준, 반복 실패 복귀 규칙을 넣는다.
5. `finishing-a-development-branch`에 조건부 Git 규칙을 넣는다.
